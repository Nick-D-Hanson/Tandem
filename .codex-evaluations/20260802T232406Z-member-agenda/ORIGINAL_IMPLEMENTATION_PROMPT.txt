PRIMARY OBJECTIVE

Add a robust personal “Agenda” feature through which each authenticated workspace member can independently plan an ordered list of lightweight items for today and the next one or two days.

This Agenda is intentionally independent of Tasks and Calendar Events:
- Agenda items are not Tasks.
- Agenda items are not Events.
- Agenda items have no category, assignee, priority, due time, recurrence, notes, or completion state.
- Creating, editing, moving, or deleting an Agenda item must not create or mutate a Task or Event.
- Do not add conversion or synchronization behavior in this implementation.

IMPORTANT NAMING CONFLICT

The calendar currently has a calendar view named “Agenda” and internally uses the `agenda` calendar mode/query value.

Resolve the user-facing conflict as follows:
- The new top-level personal feature is labeled “Agenda.”
- Rename only the existing calendar view’s visible label from “Agenda” to “My List.”
- Preserve its internal mode, URL query value, behavior, and compatibility unless the existing code makes a safer equivalent approach necessary.
- Do not remove or materially redesign the existing calendar My List/Agenda view.

PRODUCT DECISIONS

Treat these as approved requirements:

1. Ownership, visibility, and permissions
- Each Agenda belongs to one authenticated workspace member.
- Each member controls whether their entire Agenda is private or visible to the other current workspace member.
- Default visibility: private. This must be enforced by both the database default and application behavior.
- Visibility is list-wide, not item-specific. Do not add per-item visibility controls.
- When private, no other member may read the Agenda’s items or preference-backed presentation data.
- When visible, other members in the same workspace may read the owner’s Agenda in a clearly read-only view.
- Visibility never grants mutation rights. Only the owner may create, edit, reorder, move, delete, clear, or change preferences for their Agenda.
- A member can always read and mutate their own Agenda.
- Requests involving a private, cross-workspace, or nonexistent Agenda/item must return a generic user-safe result that does not expose row existence.
- All rows must remain workspace-scoped as defense in depth.

2. Planning horizon
- The user can choose a horizon of 1, 2, or 3 planned days.
- Default: 3 days.
- The horizon begins with today in the workspace timezone:
  - 1 day: today
  - 2 days: today and tomorrow
  - 3 days: today, tomorrow, and the following day
- Persist the preference per workspace member so it follows the user across devices.

3. Previous-day behavior
- Also inspect the immediately prior calendar day in the workspace timezone.
- If yesterday contains one or more Agenda items, display yesterday as a leading day before today.
- If yesterday has no Agenda items, do not display it.
- If the user deletes or clears the final item from yesterday, the yesterday section should disappear immediately after the successful mutation.
- Example for August 2, 2026: August 1 appears before August 2 only while August 1 still contains at least one item.
- Do not automatically display dates older than yesterday.
- Do not automatically delete older stored Agenda items.

4. Default item capacity
- Render seven editable item slots for each current/future displayed day by default.
- Seven is the selected default within the requested five-to-ten range.
- Empty slots are UI placeholders only and must not create database rows.
- The user can add an unlimited practical number of additional slots/items through an “Add item” action.
- Only non-empty trimmed item text is persisted.

5. Item behavior
- Each persisted item contains:
  - text/content
  - agenda date
  - ordering position
  - owner
  - workspace
  - timestamps
- Maximum trimmed item length: 300 characters.
- Support:
  - inline creation
  - inline text editing
  - deletion
  - clearing all items for one day with confirmation
  - drag-and-drop ordering within a day
  - drag-and-drop movement between displayed days
- Moving an item between days changes its Agenda date and normalized position.
- Reordering must remain stable after refresh.
- Do not implement checkboxes or completion state in this version.

6. Date semantics
- Agenda dates are date-only planning dates.
- Determine “today,” “yesterday,” and future dates using the workspace’s IANA timezone, not the browser timezone.
- Prefer a Postgres `date` column for the Agenda date rather than a UTC timestamp.
- Reuse and extend the existing centralized timezone utilities instead of duplicating date logic.
- Ensure behavior is correct around DST transitions and UTC date boundaries.

DATA MODEL

Add schema and a committed Drizzle migration consistent with current repository conventions.

Recommended tables:

1. `agenda_preferences`
- UUID primary key, if consistent with current schema conventions
- workspace UUID, required, foreign key to workspaces with cascade deletion
- user ID text, required, referencing the authenticated identity value used elsewhere
- visible_days smallint/integer, required, default 3
- is_shared boolean, required, default false
- created_at
- updated_at
- unique constraint on `(workspace_id, user_id)`
- check constraint restricting visible_days to 1 through 3
- index supporting workspace/user lookup
- ensure migration backfill/default leaves all existing member Agendas private

2. `agenda_items`
- UUID primary key
- workspace UUID, required, foreign key to workspaces with cascade deletion
- owner_user_id text, required
- agenda_date Postgres date, required
- content varchar/text, required
- position integer, required
- created_at
- updated_at
- index on `(workspace_id, owner_user_id, agenda_date, position)`
- database check that trimmed/non-empty content is represented if practical without creating brittle SQL
- database check that position is non-negative if consistent with repository conventions

Authorization must not rely only on foreign keys.

Every mutation must explicitly filter by:
- active workspace ID
- authenticated user ID matching owner_user_id
- item ID where applicable

Every read must explicitly enforce one of these cases:
- the authenticated user is the owner; or
- the authenticated user is a current member of the same workspace and the owner’s `agenda_preferences.is_shared` value is true

Never infer sharing from item possession alone. Sharing is controlled by the owner’s preference row.

Do not add Postgres row-level security; the current application intentionally uses server-only database access and application-layer authorization.

APPLICATION DATA AND SERVER ACTIONS

Use server actions and the current server-first architecture.

Implement or adapt:
- A scoped Agenda data loader that retrieves:
  - the authenticated user’s preference and editable Agenda for yesterday through two days after today
  - any other current workspace member’s Agenda only when that owner’s `is_shared` preference is true
  - only the date window required by each owner’s stored visible-days preference, plus yesterday when it contains items
- Return explicit ownership/read-only metadata to the client; never let the client infer mutation permission.
- Avoid adding all historical Agenda rows to the main AppData payload.
- Prefer route-specific loading for `/app/agenda` if that fits the repository cleanly.

Add validated server actions for:
- updateAgendaVisibleDays
- updateAgendaVisibility
- createAgendaItem
- updateAgendaItem
- deleteAgendaItem
- clearAgendaDay
- reorderAgendaItems / moveAgendaItems

Validation:
- Use Zod and existing result/error conventions.
- Validate UUIDs.
- Validate ISO date-only strings.
- Validate trimmed content length from 1 through 300.
- Validate visible days as exactly 1, 2, or 3.
- Validate visibility as an explicit boolean or closed enum mapped to `is_shared`; never accept an arbitrary member/user ID as the visibility authority.
- Reject dates outside the currently editable window of yesterday through two days after today, calculated in the workspace timezone.
- The prior day may be edited or cleared only when it already contains persisted items.
- Do not trust dates, owner IDs, workspace IDs, or positions from the client without server validation.
- Return user-safe errors without exposing whether another user’s row exists.
- Permit read-only loading of another member’s Agenda only when the current preference is shared.
- Re-check sharing on every server read; do not rely on stale client state.
- All item and preference mutations must reject non-owners even when the Agenda is shared.

Reordering transaction:
- Accept the minimum payload needed to describe the resulting ordered IDs for affected displayed dates.
- Re-fetch all referenced rows inside the transaction.
- Confirm every referenced item belongs to the authenticated user and active workspace.
- Confirm target dates fall in the allowed window.
- Confirm no unauthorized or duplicate IDs are supplied.
- Update date and normalized position atomically.
- Ensure items omitted from an affected day are not accidentally deleted.
- Prefer a clear, auditable implementation over clever fractional-position logic.

Concurrency:
- No real-time subscription is required.
- Follow the current mutation + revalidation + `router.refresh()` model.
- The UI should remain correct after refresh.
